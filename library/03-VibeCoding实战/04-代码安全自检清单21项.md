# 04 · Vibe Coding 代码安全自检清单（21 项）

> **一句话**：这是一份**给不懂代码的人**用的验收清单 —— 你不需要看懂代码，只需要照着问、照着看。
> **原件**：21 张卡片图已归档在 [`./assets/`](./assets/)（`01-安全边界表.jpg` ~ `21-一页速查.jpg`）

---

## 使用方式

1. 打开 `05-安全自检提示词汇总.md`，把提示词逐条丢给 AI
2. 拿它给的回答，对照每项的「**你看什么**」判断
3. 看不懂就执行第 21 项的保底动作：**让它用大白话重讲**

> 清单里有多处标注「**该张可跳过**」—— 不涉及对应功能就不必查，避免过度测试。

---

# 一、底线与前提（01）

## 01 · 先要一张「安全边界表」

**核心**：后端安全不是一个开关，是请求进来要过的一道道关卡。**先让 AI 把关卡摊开，别信「我做了安全处理」一句带过。**

**要点**：

- 关卡包括：登录状态、系统权限、输入校验、数据归属、注入……**少一道就是一个口子**
- **先有全景，再逐项深挖**，你才不会被 AI 一句话糊弄过去

**对 AI 说**：

```
请根据项目架构设计文档和当前业务功能，输出后端安全边界表。不要只说已做安全处理。
请按接口输入、登录状态、系统权限设计、密码规则、数据归属、注入风险分别说明：
风险是什么、当前在哪里处理、处理规则是什么、如何验证，哪些还没有验证。
```

**你看什么**：每条防线有没有落到具体位置。**这张表都说不清，就别急着问「能不能上线」。**

# 二、入口与身份（02–06）

## 02 · 接口输入 —— 前端传过来的都默认不可信

**核心**：后端接口是公开的。真想钻空子的人用工具就能**绕开整个前端**，直接对着后端发请求。

**要点**：

- 你在页面上做的**格式校验、按钮置灰、字段隐藏，对他们一点用没有**
- 价格、数量、角色、用户 ID、订单归属这些影响结果的东西，**后端必须重新判断一遍**，不能前端传了就当真的

**对 AI 说**：

```
请审查前后端接口的输入安全。不要只说已做参数校验，请按接口说明：
哪些参数来自前端，哪些参数会影响身份、系统权限、金额、库存、数据归属或数据库写入；
每个关键参数在哪里校验；校验失败返回什么；是否有示例请求证明。
```

**你看什么**：它有没有把「**关键输入**」和「普通输入」分开。关键输入错了，就是**越权、改错数据、金额或库存出错**。

---

## 03 · 登录与权限 —— 登录 ≠ 什么都能做

**核心**：**登录是确认「你是谁」，权限是确认「你能做什么」。** 登录通过，不代表这条数据你就能动。

**要点**：

- **垂直越权**：普通用户调用了本该只有管理员能用的接口（改别人角色、删后台数据）
- **水平越权**：人登录合法，却把链接里的订单号一改，就看到了别人的订单
- 很多项目只做了「要不要登录」，漏掉「**登录之后能不能动这条数据**」—— 水平越权大多这么来的

**对 AI 说**：

```
请根据项目功能设计文档，输出系统权限设计表。每个接口都要说明：
是否需要登录、允许哪些角色访问、是否只能操作自己的数据、管理员是否可以访问、
权限判断在哪个文件或中间件处理、无权限时返回什么、有没有测试证明。
```

**你看什么**：多角色项目（用户 / 商家 / 运营 / 管理员），**权限要提前定清，别让 AI 每次现搞**。

---

## 04 · 会话与登录状态 —— 那张「令牌」要管好

**核心**：登录之后，系统靠一张「令牌」认得你是谁。**这张令牌要是管不好，等于钥匙配了一堆到处丢。**

**要点**：

- **要有有效期**：长期不失效，一次泄露就等于永久可用
- **退出登录、改密码后，旧令牌必须立刻失效** —— **这条最常被漏掉**
- **别放在容易被偷的地方**：用 cookie 存的话，要开 `HttpOnly`、`Secure`、`SameSite` 这几个开关
- **优先用成熟方案**：让 AI 用所选框架或成熟认证库的会话机制，**别自己造一套**

**对 AI 说**：

```
请审查当前登录状态（会话/令牌）的安全：令牌怎么生成、存在哪里、有效期多长、
退出登录和修改密码后旧令牌是否立即失效、cookie 是否设置了 HttpOnly/Secure/SameSite、
是否使用了框架或成熟认证库而不是自己实现。逐项说明现状，没做的标为未验证。
```

**你看什么**：用没用成熟认证方案；**「退出 / 改密码后旧令牌失效」这条尤其别漏**。

---

## 05 · 密码与账号 —— 哈希存储 + 拦住弱密码

**核心**：攻击者**不是手动猜密码**，而是拿几百万条常见密码让程序批量试（暴力破解），`123456` 几秒就被试出来。

**要点**：

- **怎么存**：密码**绝不能明文进数据库**，必须先经过**哈希**（一种不可逆的处理）再存。数据库一旦泄露，明文密码等于直接公开
- **管理员尤其严**：它出事影响的不是**一个用户**，是**整个系统**

**对 AI 说**：

```
请审查当前后端的账号和密码安全规则。请说明注册、登录、修改密码、重置密码、
创建管理员账号分别在哪里校验密码强度。请检查是否包含密码长度、字符组合、
常见弱密码拦截、密码是否哈希存储（禁止明文保存）、登录失败次数限制、
管理员账号额外要求。没有实现的项目标记为未验证，不要默认安全。
```

**你看什么**：至少确认三件 —— **密码规则存在、管理员账号有更严要求、后端真会拦截弱密码。**

---

## 06 · 接口限流与防刷 —— 别让人无限次调用

**核心**：接口默认是「**不限量**」的。有人写个脚本反复调用，就能**猜密码、把你短信费刷爆、把服务器压垮**。

**要点**：

- 登录、注册、找回密码、发短信 / 邮件验证码这些接口，**必须限制同一账号、同一 IP 的请求频率**
- 登录多次失败要**锁一会儿，或加验证码**
- **花钱、耗资源的操作**（发短信、导出大数据、调用付费 AI）尤其要防刷

**对 AI 说**：

```
请检查当前项目对登录、注册、找回密码、发送短信/邮件验证码，以及花钱或耗资源的接口，
有没有做频率限制和防刷；是否限制单账号/单 IP 的调用频率，登录失败是否有锁定或验证码，
短信邮件是否防轰炸。没做的请标出并给出方案。
```

**你看什么**：**至少登录和「发短信 / 验证码」两处要有限制** —— 这两处最常被刷、最烧钱。

# 三、数据处理风险（07–13）

## 07 · 注入 —— 用户填的内容，别被当成命令执行

**核心**：注入的原理一句话 —— **用户输入本该只是「数据」，却被后端当成「指令」执行了。**

**要点**：

- 最典型是 **SQL 注入**：后端把用户填的内容**直接拼进**数据库查询语句，别人就能在输入框里填一段精心构造的内容，让数据库**绕过登录、甚至拖走整张用户表**
- 数据库之外，**系统命令、HTML、模板拼接**也有同类问题

**对 AI 说**：

```
请检查当前接口是否存在注入风险。重点检查 SQL 注入、数据库查询注入、命令注入、
HTML 或模板内容注入。请说明哪些位置使用了框架 ORM、参数化查询、白名单校验、
内容转义或内容清洗；如果存在字符串拼接用户输入的情况，请标记为风险并给出修复方案。
```

**你看什么**：**别接受「已经过滤」。** 只让它讲清一件事 —— 用的是**框架 / 数据库自带的成熟方案**，还是**它自己临时写的过滤代码**。**后者还拍胸脯说安全，要特别警惕。**

---

## 08 · 文件上传 —— 能上传东西的地方最危险

**核心**：只要你的应用能上传东西（头像、图片、附件），就是**攻击者最爱的入口**。

**要点**：

- **别只看后缀名**：改个文件名就能骗过去，要按**文件的真实内容**校验类型
- **限制大小**：防止一个超大文件把硬盘或服务撑爆
- **存到不能被网页执行的地方**：别让别人上传一个伪装成图片的脚本、再访问它、让服务器**把它跑起来**
- **重命名**：别拿用户的原始文件名直接落地

**对 AI 说**：

```
请审查当前文件上传功能的安全：是否只按后缀名判断类型（应按文件真实内容校验）、
有没有大小限制、上传文件存在哪里、是否可能被当作脚本执行、是否重命名、
访问时有没有权限控制。逐项说明。
```

**你看什么**：最要命的一条 —— **上传的文件绝不能被杀毒服务或浏览器当脚本执行**。
> 项目没有上传功能，**这张可跳过**。

---

## 09 · 跨站与安全响应头 —— 浏览器侧的坑

**核心**：这几项是浏览器侧的坑，好在**大多能靠框架自带能力或几行配置解决**，关键是**别关掉、别配错**。

**要点**：

- **CSRF（跨站请求伪造）**：别人诱导你在已登录状态下，悄悄替你发一个操作请求。**用 cookie 登录的网站要防**，优先用框架自带的 CSRF 防护，配合 `SameSite` cookie
- **安全响应头**：一组告诉浏览器"怎么更安全地对待你网站"的开关（如 CSP、HSTS），**开启成本低、收益高**
- **CORS（跨域）**：控制"哪些外部网站能调用你的接口"，**别图省事设成"谁都能调"**

**对 AI 说**：

```
请检查当前项目的 CSRF 防护（尤其用 cookie 登录时，是否启用框架自带的 CSRF 防护和
SameSite cookie）、是否配置了常见安全响应头（如 CSP、HSTS）、CORS 跨域是否被设成
允许任意来源。逐项说明现状和建议，优先使用框架自带能力。
```

**你看什么**：**别接受「为了方便先允许所有跨域」这种设置**；能用框架自带就别自己造。
> 纯后端接口项目，CSRF 这条按登录方式判断是否适用。

---

## 10 · 外部请求（SSRF）—— 拿用户给的网址去访问要当心

**核心**：如果你的功能会「**拿一个网址，让服务器去访问它**」（按链接抓图、回调 webhook、调用外部接口），就要防 SSRF。

**要点**：

- **现象**：攻击者填一个指向你**内部系统**的地址，借你的服务器去访问本不该被外部碰到的**内网资源**
- 用户能填网址的地方，后端要用**白名单**（只允许访问指定域名），**而不是黑名单**
- **禁止访问内网地址**和云服务器的「**元数据地址**」

**对 AI 说**：

```
我的项目里有没有「根据用户提供的网址，由服务器去请求」的功能（如抓取链接、
上传网络图片、webhook、调用外部 API）？如果有，请检查是否存在 SSRF 风险：
是否用白名单限制了可访问的域名、是否禁止访问内网和云元数据地址。逐项说明并给出修复。
```

**你看什么**：**没有**「服务器去请求用户给的网址」这类功能，这张可跳过。**有就必须用白名单。**

---

## 11 · 数据库操作 —— 重要数据不能随便查、改、删

**核心**：数据库安全不止「能不能连上」，更要紧的是**谁能查、谁能改、谁能删**。

**要点**：

- **删除要谨慎**：用户、订单、支付记录这类数据，**别直接物理删除**（真抹掉）；更稳的是**软删除**（只标记"已删除"，需要时能找回，很多框架自带 `deleted_at`）
- **多张表一起变动，必须用事务**：比如下单时同时动订单、库存、优惠券 —— **要么全成功要么全不算**，不然会出现「**订单建了、库存没扣**」的烂账
- **操作必须绑业务规则**：**能查到一条数据，不代表这个人有权操作它**

**对 AI 说**：

```
请审查当前后端数据库操作安全。请按数据表或数据模型列出：哪些是重要数据，
哪些接口会读取它，哪些接口会修改它，哪个接口会删除它；每个操作是否经过身份校验、
权限校验、数据归属校验和业务规则校验；是否存在直接根据前端传入的 ID 修改或删除数据
的情况；是否有软删除、事务或审计日志要求。
```

**你看什么**：有没有「**直接拿前端传来的 ID 就改 / 删数据**」的情况 —— **这正是水平越权的温床**。

---

## 12 · 业务逻辑与并发 —— 功能跑通，也可能被钻规则空子

**核心**：有些漏洞不是「技术漏洞」，是**业务规则没兜住** —— 功能都跑通了，却被人钻了规则的空子。

**要点**：

- **金额、数量、积分后端要按真实规则重算**：别信前端传来的（比如有人把价格改成 `0.01`）
- **防重复提交和并发**：同一个「下单」「领券」「提现」被同时间点很多次，会不会**超卖、超额、重复扣款**？要用**事务、库存校验、幂等**（同一操作做多次结果一样）兜住
- **关键步骤不能跳**：比如**没付款就变成「已发货」**

**对 AI 说**：

```
请审查当前核心业务流程（下单、支付、退款、领券、提现等）的业务逻辑安全：
金额/数量/库存是否由后端按业务规则重新校验、是否防止重复提交和并发导致的
超卖/超额/重复扣款、关键步骤是否能被跳过。逐项说明并举例风险。
```

**你看什么**：重点看「**能不能重复提交**」「**金额是不是后端说了算**」—— 电商、支付类项目最容易栽在这。

---

## 13 · 敏感数据保护 —— 不止密码

**核心**：密码要哈希（前面讲了），但**敏感数据不止密码** —— 手机号、身份证、银行卡、聊天内容，**传输和存储都要保护**。

**要点**：

- **传输**：全站走 **HTTPS**（加密通道），别用明文传密码和隐私（证书在部署时落地）
- **存储**：身份证、银行卡这类高敏感数据，**要么加密存，要么脱敏**（只存部分）
- **最小收集**：用不到的敏感信息**就别收集、别存**，也别在接口里返回给前端

**对 AI 说**：

```
请审查当前项目对敏感数据（密码、手机号、身份证、银行卡、支付信息等）的保护：
传输是否强制 HTTPS、哪些敏感数据在数据库里是明文、是否需要加密或脱敏、
接口返回给前端时有没有把不该给的敏感字段也带出去、有没有收集了其实用不到的敏感信息。
逐项说明。
```

**你看什么**：特别看「**接口有没有把不该给前端的敏感字段也返回了**」—— **这是最常见的泄露**。

# 四、工程卫生（14–17）

## 14 · 别过度防御 —— 安全不是把代码堆复杂

**核心**：一听「安全」，有的 AI 会**滑向反面** —— 给根本不可能发生的情况也写判断。

**要点**：

- 前面已强制登录，后面又反复判断「如果没登录怎么办」；这类**永远走不到的分支叫死代码**
- **它不增加一分安全**，只会让代码更乱、把真正的业务逻辑淹没

**对 AI 说**：

```
请审查当前接口安全逻辑是否存在过度防御。请区分：必须校验的业务规则、
框架已经处理的基础校验、可以由前端体验层处理的提示校验，以及永远不会触发的
防御分支（死代码）。不要为了安全感新增重复判断或不可能成立的条件。
任何新增安全封装都必须解释解决什么真实风险。
```

**你看什么**：**该严的地方**（是否登录、是否有权限、金额库存是否合规）**必须严**；**不该复杂的地方别乱加**。

---

## 15 · 配置与密钥 —— 秘密绝不能写死在代码里

**核心**：AI 图方便，常把**数据库地址、各种密钥、管理员初始密码直接写死在代码里**。本地跑没事，代码一旦被**提交、分享、部署**，秘密就跟着暴露。

**要点**：

- 别人拿到数据库密码就能**连库导数据**，拿到支付密钥就能**冒用你扣钱**，而你可能毫不知情

**对 AI 说**：

```
请检查当前后端项目是否存在敏感配置写死在代码里的情况。重点检查数据库地址、
数据库密码、登录令牌密钥（如 JWT）、第三方接口密钥、管理员初始密码、支付或通知相关密钥。
请输出：配置名称、当前所在位置、是否来自环境变量、是否出现在代码或仓库中、
是否登记在对应的配置示例文件（如 .env.example，具体按所用框架而定）、是否需要更换。
```

**你看什么**（四条）：

1. **真密钥绝不出现在代码里**
2. **示例文件只写占位、不写真值**
3. **代码从环境变量读配置**
4. **之前写死过的密钥，让它明确回答要不要换掉**

---

## 16 · 日志 —— 别把敏感信息原样记下来

**核心**：日志本来是排查问题用的，但**密码、token、手机号、身份证号、支付内容不该原样写进去** —— 日志一泄露，等于**又开一个口子**。

**要点**：

- 关键功能还要**主动埋日志**（登录、注册、下单、支付、任何增删改重要数据），方便上线后出事排查

**对 AI 说（查日志有没有泄露）**：

```
请审查当前前后端日志安全。请说明请求日志、错误日志、数据库日志分别记录哪些内容、
是否会记录密码/token/密钥/手机号/身份证号/支付信息等敏感数据。如果会记录，
请说明如何脱敏或移除。请给出一条正常请求日志和一条错误日志示例。
```

**对 AI 说（给关键功能埋日志）**：

```
请在我这些关键功能上，加上必要的运行日志——登录、注册、下单、支付，以及所有
涉及金额和重要数据的操作。记录关键步骤、传入的关键信息和最终结果，方便我上线后
排查问题。注意：日志里绝对不要打印密码、密钥这类敏感信息。
```

**你看什么**：**哪些能记、哪些不能记、敏感内容有没有脱敏**（如手机号只留前三位）。

---

## 17 · 依赖安全 —— 你用的框架和 SDK 本身也会爆漏洞

**核心**：漏洞不一定是你写错了，**也可能是你用的那个库出了问题连累你**。

**要点**：

- 比如 **Log4j** 当年爆出严重漏洞，攻击者能**直接在服务器上运行命令**，没及时升级的项目就一直暴露着
- AI 写代码用的往往是**它知道的某个版本**，它**不会主动帮你盯**这个库后来有没有爆新漏洞

**对 AI 说**：

```
请列出当前后端项目用到的所有框架、第三方库和 SDK，以及各自的版本。请逐项说明：
有没有已知的安全漏洞或安全公告，当前版本是不是官方建议升级的版本，如果需要升级，
会影响哪些现有功能。请重点标出那些负责网络请求、登录认证、加密、文件上传、
数据库连接的依赖。
```

**你看什么**：**升级别让 AI 随便来。** 先让它说清这次升级**解决什么、会不会影响现有功能**，确认了再升。

# 五、收尾与验收（18–21）

## 18 · 清掉「基础代码」—— 临时接口是明晃晃的窟窿

**核心**：AI 做功能时经常顺手留下**测试打印、假数据、临时测试接口**，而且**它不会自己删** —— 你不提，它就永远留着。

**要点**：

- **最危险的是没有权限校验的临时接口**（能跳过登录、直接改数据），一旦跟着上线，**别人能直接拿来操作你的数据**
- **时机**：功能写完、测试通过、**你自己也用过确认没问题**，之后再清

**对 AI 说**：

```
这个功能已经开发完成，测试也通过了。请列出本次开发过程中，你为了调试、测试、
临时验证而新增的代码，包括临时测试文件、调试打印、临时测试接口、写死的假数据、
一次性脚本等。请逐项说明：它在哪个文件、当初做什么用、现在还需不需要。可以删的
请删掉；不确定的先列出来让我决定。不要动正式的业务代码、正式的回归测试，以及我
有意留在关键功能上、用来上线后排查问题的运行日志。
```

**你看什么**：**删完再跑一遍正式测试。** 别让它把该留的一起删了 —— **正式回归测试、关键功能上的运行日志，都得留着**。

---

## 19 · 验收 —— 让 AI 切换角色，测「出错会不会被拦」

**核心**：安全不能靠一句「已经处理了」。它不能只站在**写代码的角度**说「我写了校验」，还要站在**没权限的人、发异常请求的人**的角度去试。

**要点**：

- 一个接口**只能证明「正常请求跑得通」、却证明不了「错误请求会被拦住」，就不算验收完成**

**对 AI 说**：

```
请对本次新增或修改的接口做安全和业务双重验收。请输出：正常请求示例、参数错误示例、
未登录示例、无权限示例、越权访问他人数据示例、数据库写入或修改前后的证据、
日志记录证据。请说明哪些测试是通过接口完成，哪些测试是通过数据库检查完成。
没有实际验证的项目标记为未验证。
```

**你看什么**：有没有覆盖这几类 —— **正常能用、出错会拦、没权限过不去、数据不越界、数据库结果对得上、关键过程日志能查到。**

---

## 20 · 上线前总检 —— 一张清单从头过一遍

**核心**：临上线是最后一道关。最该绷紧的一根弦是 —— **开发和上线，必须是两套环境。**

**要点**：

- **连的数据库不同、用的密钥不同、域名分开**
- **生产环境的「调试模式」必须关掉**（不然一报错就把内部细节、敏感信息**显示给所有访问的人看**）
- 再核一遍：密钥没写死、测试全通过、临时接口和垃圾代码清干净、上线数据库没有测试数据、越权和注入、关键功能日志

**对 AI 说**：

```
我准备把这个项目部署上线。请根据项目实际情况，帮我列一份上线前检查清单，
并逐项检查、告诉我结果。至少包括：开发环境和生产环境是不是彻底分开（数据库、
密钥、域名各用各的）、生产环境的调试模式有没有关、密钥和敏感配置有没有写死在
代码里、所有测试是否全部通过、调试用的临时接口和垃圾代码有没有清理、上线数据库里
有没有残留测试数据、有没有越权和注入风险、关键功能有没有加好必要的运行日志
（且日志里不含密码密钥）。如果是 web 项目，还要检查多浏览器兼容性和前端性能体验。
```

**你看什么**：**这根弦松了后面再小心都白搭** —— 开发的归开发，上线的归上线，**绝不可拿开发那套直接顶上去**。

## 21 · 一页速查（封底 / 合集）

**核心**：**全程唯一的保底动作** —— **任何一条 AI 的回答你看不懂，就让它用大白话重讲。看不懂的验收，等于没验收。**

**要点（19 条速查）**：

| # | 项目 | 一句话 |
|---|---|---|
| 02 | 接口输入 | 关键数据后端**重新判断一遍** |
| 03 | 登录权限 | 登录 ≠ 能动这条数据，防**垂直 / 水平越权** |
| 04 | 会话令牌 | 有有效期，**退出 / 改密后旧令牌失效** |
| 05 | 密码账号 | **哈希存储**、拦截弱密码，管理员更严 |
| 06 | 限流防刷 | 登录、发短信 / 验证码**必须限频** |
| 07 | 注入 | 用**框架 / 数据库成熟方案**，别信自造过滤 |
| 08 | 文件上传 | 按**真实内容**校验，上传物**绝不能被执行** |
| 09 | 跨站 / 跨域 | CSRF **用框架自带**，别允许任意跨域 |
| 10 | SSRF | 服务器去请求用户给的网址，要用**白名单** |
| 11 | 数据库 | 查改删**绑业务规则**，多表变动用**事务** |
| 12 | 业务并发 | **金额后端说了算**，防重复提交 / 超卖 |
| 13 | 敏感数据 | 传输走 **HTTPS**，别把敏感字段返回前端 |
| 14 | 过度防御 | **该严的严**，别堆死代码 |
| 15 | 配置密钥 | **绝不能写在代码里** |
| 16 | 日志 | **不记敏感信息**，关键功能埋日志 |
| 17 | 依赖 | 定期查漏洞，**升级先评估** |
| 18 | 基础代码 | 清临时接口 / 假数据，**别删回归测试和关键日志** |
| 19 | 验收 | **切换角色**测「出错会不会被拦」 |
| 20 | 上线前 | **开发 / 生产两套环境**，调试模式必须关 |
